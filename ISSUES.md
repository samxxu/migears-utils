## Verdict / 结论

The paginator semantics are now consistent, but hardening the host validator introduced the round's only P0: the new regular expressions use `$` anchors, and in PCRE `$` also matches before a trailing newline, so a host or scheme ending in a single LF passes validation and lands in the authority.

分页器语义现已一致，但新加的 host 校验引入了本轮唯一的 P0：新正则用了 $ 锚点，而 PCRE 的 $ 还允许匹配结尾换行之前，因此以单个 LF 结尾的 host 或 scheme 能通过校验并进入 authority。

## Fixed since the last round / 本轮已修复确认

上一轮 P1 与四条 P2 全部修复：hasMore 与 nextCursor 的冲突（空 items 强制 hasMore=false、末条无游标即抛）、两分页器的 pageSize 归一化对齐、端口 1–65535 校验、host 的常规非法字符（CRLF/空格/斜杠/@/坏转义）与 query 中 null 在两个方法间的一致性。

### P0

**P0-1** — `src/URL.php:61,376,377`

- EN: The scheme, reg-name and IP-literal patterns use `$` without `/D` or `\z`, so a single trailing LF slips through the character classes even though `\n` is excluded. Reproduced: `new URL("https", "example.com\n")->toString()` yields `"https://example.com\n/"`; `new URL("https\n", "example.com")` yields an authority preceded by a raw LF; the same works via `withHost()`. `"example.com\r\n"` is correctly rejected, which is why only the single-LF form escapes. The module sells itself as safe URL building and the changelog promises the host rule stops spaces, CRLF and path separators from entering the request line. In PCRE the `$` anchor also matches before a trailing newline<sup><a href="#cite-4">[4]</a></sup>, which is precisely why the single-LF form escapes.
- 中文: 方案、reg-name 与 IP 字面量的正则使用 $ 且未加 /D 或 \z，因此尽管字符类排除了 \n，结尾单个 LF 仍被放行。实测：new URL("https", "example.com\n")->toString() 得到 "https://example.com\n/"；new URL("https\n", "example.com") 产出以裸 LF 开头的 authority；withHost() 同样可复现。"example.com\r\n" 会被正确拒绝，这正是只有单 LF 形态逃逸的原因。本模块自我定位为安全 URL 构建，变更日志也承诺 host 规则可阻止空格、CRLF 与路径分隔符进入请求行。PCRE 的 <code>$</code> 还会匹配结尾换行之前<sup><a href="#cite-4">[4]</a></sup>，这正是单 LF 形态得以逃逸的原因。
- Verification / 验证: reproduced / 已实证


### P3

**P3-1** — `src/URL.php:321-335,239`

- EN: Query rebuilding is form-encoded and not byte-preserving: `URL::parse("https://example.com/?a%20b=1")->toString()` yields `?a+b=1`, and `+` is decoded to a space. The README's "already-encoded URL survives a parse-and-rebuild cycle unchanged" reads as global but is scoped to path/fragment.
- 中文: query 重建使用 form 编码、不保字节：URL::parse("https://example.com/?a%20b=1")->toString() 得到 ?a+b=1，且 + 会被解码成空格。README 的「已编码 URL 经解析重建后不变」读起来像全局承诺，实际只覆盖 path 与 fragment。
- Verification / 验证: reproduced / 已实证

**P3-2** — `src/URL.php:89,393-396`

- EN: `query()` and `toString()` still disagree for non-string scalars: with `query: ["flag"=>true,"n"=>5]`, `query()` returns the original values while `toString()` emits `?flag=1&n=5`. Only `null` was unified.
- 中文: query() 与 toString() 对非字符串标量仍不一致：query: ["flag"=>true,"n"=>5] 时 query() 返回原值而 toString() 输出 ?flag=1&n=5。上一轮只统一了 null。
- Verification / 验证: reproduced / 已实证
