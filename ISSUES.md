## P1

### P1-1

- **Status / 状态**: Fixed / 已修复
- **Where / 位置**: `src/FlowPaginator.php:46-72` (constructor guard), `116-124` (`nextCursor()`), `136-154` (`withItems()`), `156-172` (`nextPage()`)
- **Verification / 验证**: reproduced before fix, regression tests added — `testHasMoreWithoutCursorValueThrows`, `testObjectItemWithoutCursorPropertyThrows`, `testNullCursorValueCountsAsUnusable`, `testExceptionNamesTheConfiguredColumn`, `testNextPageThrowsWhenLastItemLacksCursorValue`, `testWithItemsThrowsWhenLastItemLacksCursorValue`, `testHasMoreAlwaysComesWithUsableCursor`, `testItemsWithoutCursorValueAreFineWhenHasMoreIsFalse`
- **EN**: `hasMore = true` and `nextCursor() === null` can hold at the same time (when an item lacks the `cursorColumn` the cursor is **silently null**). A consumer that trusts `hasMore` loops back to the first page forever; `nextPage()` and `withItems()` likewise cannot distinguish "no next page" from "next page but no cursor". **Fixed**: the constructor now rejects `hasMore: true` when the last item yields no value for the cursor column, so `hasMore` implies a usable cursor on every path, since `nextPage()` and `withItems()` both funnel through the constructor. The exception names the column and both ways out; a missing cursor value stays acceptable when `hasMore` is false, and an empty page still ends the sequence.
- **中文**: `hasMore = true` 与 `nextCursor() === null` 可以同时成立（条目缺 `cursorColumn` 时**静默返回 null 游标**）。消费方若以 `hasMore` 为准会无限回到首页；`nextPage()` 与 `withItems()` 同样无法区分「没有下一页」与「有下一页但取不到游标」。**已修复**：构造器现拒绝「最后一条没有游标列取值」与 `hasMore: true` 的组合，故 `hasMore` 在任何路径上都意味着游标可用（`nextPage()` 与 `withItems()` 都经过构造器）。异常消息点名该列并给出两条出路；`hasMore` 为 false 时仍允许缺少游标值，空页仍然终止序列。

## P2

### P2-1

- **Status / 状态**: Fixed / 已修复
- **Where / 位置**: `src/FlowPaginator.php:53` vs `src/Paginator.php:39`
- **Verification / 验证**: reproduced before fix, regression tests added — `testPageSizeIsRaisedToOne`, `testPageSizeAgreesWithPaginator`
- **EN**: The two paginators normalise the same parameter in opposite ways: `new FlowPaginator(pageSize: 0)->pageSize === 0` while `new Paginator(pageSize: 0)->pageSize === 1`. Two DTOs in one package, two semantics. **Fixed**: `FlowPaginator` now applies `max(1, $pageSize)` like `Paginator`, so the two agree; `testPageSizeAgreesWithPaginator` pins the two implementations to each other rather than to a literal.
- **中文**: 两个分页器对同一参数归一化策略相反：`new FlowPaginator(pageSize: 0)->pageSize === 0`，而 `new Paginator(pageSize: 0)->pageSize === 1`。同包两个 DTO 两种语义。**已修复**：`FlowPaginator` 现与 `Paginator` 一致地应用 `max(1, $pageSize)`；`testPageSizeAgreesWithPaginator` 把两者互相钉住，而非各自钉住一个字面值。

### P2-2

- **Status / 状态**: Fixed / 已修复
- **Where / 位置**: `src/URL.php:71-73` (constructor; `withPort()` inherits through `with()`)
- **Verification / 验证**: reproduced before fix, regression tests added — `testPortBoundsAreAccepted`, `testPortZeroIsRejected`, `testNegativePortIsRejected`, `testPortAboveRangeIsRejected`, `testWithPortValidatesToo`
- **EN**: `URL` does not validate the port range: `port=0` produced `https://example.com:0/`, `-1` produced `:-1/` and `70000` produced `:70000/`, all verbatim. **Fixed**: the constructor requires 1–65535. Throwing rather than clamping is deliberate — silently rewriting a port would connect somewhere the caller did not name. `parse()` inherits the rule, so `parse('http://example.com:0/')` now throws too (a string with `:70000` was already rejected by `parse_url()`).
- **中文**: `URL` 端口无 0-65535 校验：实测 `port=0` → `https://example.com:0/`、`-1` → `:-1/`、`70000` → `:70000/` 原样输出。**已修复**：构造器要求 1–65535。选择抛异常而非静默改写是有意的——悄悄改掉端口会把请求发往调用方并未指定的地方。`parse()` 同样受此约束，故 `parse('http://example.com:0/')` 现也抛出；含 `:70000` 的字符串此前已被 `parse_url()` 拒绝。

### P2-3

- **Status / 状态**: Fixed / 已修复
- **Where / 位置**: `src/URL.php:69` (call), `374-386` (`assertValidHost()`)
- **Verification / 验证**: reproduced before fix, regression tests added — `testHostWithCrlfIsRejected`, `testHostWithSpaceIsRejected`, `testHostWithPathSeparatorIsRejected`, `testHostWithAtSignIsRejected`, `testMalformedPercentEscapeInHostIsRejected`, `testWithHostValidatesToo`, plus `testUnderscoreHostIsAccepted` and `testIpv6LiteralRoundTrips` to pin what must keep working
- **EN**: The host is not validated either: `new URL('https', "example.com\r\nX-Injected: yes")` produced an authority containing CRLF. As a "safe URL building" tool, feeding that to an HTTP client is a request-injection surface. **Fixed**: the constructor accepts an RFC 3986 reg-name (unreserved, sub-delims, valid percent escapes) or a bracketed IP literal, and rejects everything else. The set was chosen for what it excludes — space, CR, LF, and the characters that end or redirect the authority (`@`, `/`, `?`, `#`) can no longer appear — while still admitting underscore hosts, IPv4, and `[::1]`. Being permissive rather than hostname-strict keeps RFC-legal names working; `parse_url()` keeps the brackets, so an IPv6 URL round-trips unchanged.
- **中文**: host 不校验字符：实测 `new URL('https', "example.com\r\nX-Injected: yes")` 产出含 CRLF 的 authority。作为「safe URL building」工具，下游用于 HTTP 客户端即存在请求注入面。**已修复**：构造器接受 RFC 3986 的 reg-name（unreserved、sub-delims、合法百分号转义）或方括号 IP 字面量，其余一律拒绝。选择这个集合的理由在于它排除了什么——空格、CR、LF，以及会终结或改写 authority 的字符（`@`、`/`、`?`、`#`）都无法再出现——同时仍允许下划线主机名、IPv4 与 `[::1]`。采用宽松而非「仅主机名字符」的规则，是为了不误伤 RFC 合法名称；`parse_url()` 会保留方括号，故 IPv6 URL 往返不变。

### P2-4

- **Status / 状态**: Fixed / 已修复
- **Where / 位置**: `src/URL.php:89` (constructor), `167-170` (`withQuery()`), `393-396` (`withoutNulls()`)
- **Verification / 验证**: reproduced before fix, regression tests added — `testConstructorDropsNullQueryValues`, `testQueryAndToStringAgreeAboutNulls`, `testWithQueryDeletesWithNull`, `testDeletingTheLastParameterLeavesNoQuestionMark`, `testNullQueryValueDoesNotSurviveAMerge`
- **EN**: Two methods of the same instance disagree about `null`: constructing with `['a' => null, 'b' => 1]` makes `query()` return `{"a":null,"b":1}` while `toString()` emits `?b=1` via `http_build_query`; and `withQuery(['a' => null])` means "delete", contradicting the constructor accepting null. **Fixed**: `null` now means "the parameter is absent" everywhere, so the class has one rule instead of two. The constructor drops null values through `withoutNulls()`, and `withQuery()` merges and lets the constructor normalise — which also collapsed a per-key loop into one line. Deleting was chosen over "serialise as an empty value": `''` already expresses an empty parameter, so giving `null` that meaning would make the two indistinguishable.
- **中文**: 同一实例两个方法对 `null` 的处理不一致：构造传 `['a' => null, 'b' => 1]` 时 `query()` 返回 `{"a":null,"b":1}`，而 `toString()` 经 `http_build_query` 输出 `?b=1`；另 `withQuery(['a' => null])` 的语义是「删除」，与构造器接受 null 自相矛盾。**已修复**：`null` 现在在任何位置都表示「该参数不存在」，全类由两条规则收敛为一条。构造器经 `withoutNulls()` 丢弃 null 值，`withQuery()` 只做合并、由构造器统一归一化——顺带把逐键循环收成一行。选择「删除」而非「序列化为空值」：`''` 已经表达空参数，若让 `null` 也表达这个意思，两者就无从区分。
