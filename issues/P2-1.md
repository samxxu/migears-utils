# P2-1 — URL::parse() uses the native parse_url() which returns false for …

## Finding / 问题

- EN: URL::parse() uses the native parse_url() which returns false for severely malformed URLs but silently truncates unusual-but-valid inputs (e.g. a scheme with underscores, or a host starting with a digit). The function does not validate that the result round-trips correctly.
- 中文: URL::parse() 使用原生 parse_url()，对严重畸形的 URL 返回 false，但对不常见但合法的输入（如下划线 scheme、数字开头的主机）会静默截断。该函数未校验结果能否正确回传。
- Where / 位置: `src/URL.php:42-58`
- Verification / 验证: static / 仅静态推断

- 2026-09-28 · `coordinator — cross-module` · `open` — added by the coordinator:
- EN: The audit reproduced this against the code on the same day and points at the call site rather than
  at the constructor, which is why the two are one item: `URL::parse()`, `URL::http()` and `URL::https()`
  validate only what `parse_url()` returns, and `parse_url()` rewrites the raw authority before the
  constructor ever sees it — a control character becomes `_` (`https://example.com\n/` →
  `https://example.com_/`), and anything after the port is dropped (`http://example.com:80abc/p` →
  `http://example.com/p`). The constructor rejects the identical values, so the class contract does not hold
  on this path. Guard at `src/URL.php:272-282`, helper `hasTruncatedPort()` at `:380-406`, tests
  `tests/URLTest.php:97,107`. Filed from the filing request of 2026-09-28, its label `A1`.
- 中文：审计于同日在这棵树上复现，并指向调用点而不是构造函数——这正是二者是同一条条目的原因：
  `URL::parse()`、`URL::http()` 与 `URL::https()` 只校验 `parse_url()` 的返回值，而 `parse_url()` 会在
  构造函数看到之前改写原始 authority：控制字符变成 `_`（`https://example.com\n/` →
  `https://example.com_/`），端口之后的内容被丢弃（`http://example.com:80abc/p` →
  `http://example.com/p`）。同一取值走构造函数则被拒绝，因此类别契约在这条路径上不成立。守卫在
  `src/URL.php:272-282`，辅助方法 `hasTruncatedPort()` 在 `:380-406`，用例 `tests/URLTest.php:97,107`。
  依据 2026-09-28 的立案请求立案，其标号为 `A1`。
